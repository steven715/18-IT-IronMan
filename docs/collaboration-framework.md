# 我的 AI 協作框架（持續收斂中）

這份文件從 Day 1 就開始寫，不是等到最後才動筆。

系列的每一天都是這份框架的素材：踩到的雷、事後的反思、下次改怎麼講。Day 30 做的是彙整，不是從零生出一份框架。

收斂過程是安靜的——不必每天在文章裡宣告「今天框架又長了一條」，素材追加到下面的表就好。

---

## 一、這份框架能主張什麼、不能主張什麼

**能主張的**：我之前踩了什麼雷、我怎麼反思、反思後得出什麼結論。這些是我親身經歷過的，有紀錄可查。

**不能主張的**：「照這份框架做可以省下多少時間」「注意力和判斷力提升了多少」。這些沒有辦法量化，樣本也只有我一個人、一個專案。頂多只能說：這些調整未來或許能幫我省下時間。

Day 30 彙整時照這個界線寫，不要越界。混淆變數的完整聲明見 [methodology.md](methodology.md)。

## 三、素材：踩雷紀錄

只追加，不刪改。每一列就是一次「我以為 AI 會知道、但它不知道」的事件。

| Day | 情境 | 我以為 AI 會知道的事 | 實際發生什麼 | 下次怎麼講 |
| --- | --- | --- | --- | --- |
| | | | | |

**填寫要點**：

- 「我以為 AI 會知道的事」這欄是核心，也是最容易寫得太籠統的一欄。寫「它不懂專案慣例」沒有用，要寫「它不知道這個專案的 error 一律往上拋、不在 service 層 catch」。
- 「下次怎麼講」寫成可以直接貼進 prompt 或 CLAUDE.md 的句子，不要寫成心得感想。
- 同一條規範重複踩到就再記一列，重複次數本身是資訊——代表這條特別容易被忽略。

## 五、維護方式

- 每天寫完文章，順手把當天的素材追加到第三節。沒有就不用寫。
- 第二節（收斂到的規則）不必每天更新。等某條規範重複出現、或看得出模式了再往上提。
- Day 26（三框架比較）與 Day 27（我怎麼評斷一套協作框架）會用到這份文件，屆時回頭讀第三節的完整紀錄，不要只憑印象。
- Day 30 彙整成正式交付版本，並保留這份過程紀錄，不要覆蓋掉。
