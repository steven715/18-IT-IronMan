# 方法論：這個系列怎麼測量「人與 AI 的協作」

本文定義整個系列共用的測量方法，所有文章的「AI 協作紀錄」章節都依此填寫。
**本文件在 Day 11 正式發表，標記為「待補」的區塊必須在 Day 11 前填完。**

---

## 一、2×2 分類

每一次 AI 產出（一個回合的回答、一段程式碼、一個結論）都落在以下四格之一。
兩個軸是：AI 產出對／錯 × 作者是否及時驗證。

「及時」的定義：在該產出被採用進下一步之前就驗證了。等到後面出事才回頭發現，不算及時。

| | 作者及時驗證 | 作者未及時驗證 |
| --- | --- | --- |
| **AI 產出正確** | **① 真槓桿** | **② 隱性風險** |
| **AI 產出錯誤** | **③ 摩擦成本** | **④ 被騙** |

### ① 真槓桿（對，且當場驗證）

AI 給的東西是對的，作者也確實看懂並確認過。這是唯一真正省到時間的格子。
記錄：次數。

### ② 隱性風險（對，但未驗證）

結果剛好是對的，但作者當下沒驗證就採用了。這格不算成功——這次對是運氣，同樣的行為模式下次就會掉進 ④。
記錄：次數。這格的數量是「我對 AI 的信任是否超出我的查核能力」的指標。

### ③ 摩擦成本（錯，但當場抓到）

AI 出錯，作者在採用前就發現並要求修正。損失的是往返時間，不是正確性。
記錄：次數，以及每次的往返輪數（從第一次提出到通過驗收，一共來回幾輪）。

### ④ 被騙（錯，且事後才發現）

AI 出錯、作者當下沒抓到、錯誤流進了後續工作，直到後面某個時點才爆出來。
記錄：次數，「多久後發現」（用「幾個回合後」或「幾天後」記，兩個都寫更好），以及是什麼讓它曝光的（測試、code review、跑起來壞掉、讀者指出）。

## 二、量表欄位

實作類文章的「AI 協作紀錄」章節填寫下表（哪些算實作類見 CLAUDE.md 的驗收規則；介紹、背景、彙整類不填）。

| 欄位 | 說明 | 記法 |
| --- | --- | --- |
| **往返輪數到驗收** | 從第一次提出需求到該項產出通過驗收，一共來回幾輪 | 整數；多個任務分別記 |
| **人工介入次數與範圍** | 作者實際動手改的次數，以及改的範圍 | 次數 ＋ 範圍分級（見下） |
| **問題由誰先發現** | 每個問題的第一發現者 | `AI 自查` ／ `作者 review` ／ `測試` |
| **錯誤類型** | 該次錯誤的性質 | 見下方分類 |
| **餵入背景的成本** | 為了讓 AI 能動工，作者花在準備上下文的工夫 | 見下方分級 |

### 人工介入範圍分級

| 分級 | 意思 |
| --- | --- |
| **微調** | 改名、格式、單行修正，不動邏輯 |
| **局部改寫** | 改一個函式／一個檔案內的邏輯 |
| **結構重來** | 推翻設計、跨檔案重做 |

### 錯誤類型分類

| 類型 | 說明 |
| --- | --- |
| **事實錯誤** | API 不存在、參數名錯、版本行為記錯 |
| **需求誤解** | 做出來的東西不是要的東西 |
| **範圍逾越** | 沒要求的地方也被改了 |
| **過時知識** | 用了專案裡已經淘汰的寫法 |
| **未驗證假設** | 假設某個檔案／欄位／設定存在，沒去確認 |
| **邏輯錯誤** | 程式跑得起來但行為錯 |
| **沉默失敗** | 出錯但回報成功 |

### 餵入背景的成本分級

| 分級 | 意思 |
| --- | --- |
| **低** | 一句話就能動工，AI 自己去讀專案 |
| **中** | 需要指定檔案、貼片段、講清楚約定 |
| **高** | 需要先寫 spec／整理現況／畫架構才能開始 |

> 當日零事件也要填表。「0 次介入、全數驗證通過」本身就是數據，代表當天的任務落在 AI 能可靠處理的範圍內。空白與零是不同的資訊。

## 三、已知混淆變數聲明

這個系列不做框架排名宣稱。以下變數在實驗設計上無法排除，先講清楚：

1. **三個功能標的本質不同。** 即時轉碼（Day 13–16）、全文搜尋（Day 18–21）、API Gateway（Day 23–25）在技術難度、不確定性、可測試性上都不一樣。即時轉碼牽涉 ffmpeg 參數與外部程序行為，全文搜尋牽涉選型與 CJK 斷詞品質，API Gateway 偏架構與設定。用不同框架做不同題目，差異來源無法歸因到框架。

2. **作者對 superpowers 較熟。** 第一輪（Day 12–16）用的是作者原本就在用的框架，另外兩套是在系列進行中才開始上手的。這對第一輪有利。

3. **熟練度隨系列累積。** 到了第三輪，作者「怎麼提問、什麼時候該驗證、什麼時候該喊停」的能力已經比第一輪好。這對後面兩輪有利，方向跟第 2 點相反，但兩者不會剛好互相抵銷成零。

4. **樣本量極小。** 每個框架只有一個功能標的加一次校準任務，任何數字差異都可能只是雜訊。

5. **作者同時是執行者與評分者。** 沒有盲測，存在期待效應。

所以本系列的結論一律是「使用報告 ＋ 條件限定」：講「在什麼前提下，我遇到了什麼」，不講「A 框架優於 B 框架」。

校準任務就是為了對抗第 1、3 點設計的——三輪各做一次同一份 spec 的同一個題目，讓不同輪次之間至少有一個共同基準。但它只能對齊「相同題目下的表現」，消不掉熟練度累積，這點在解讀時要一起講。

## 四、校準任務 spec：播放遙測 endpoint

三輪各執行一次，spec 完全相同，不因框架調整。

題目：`POST /api/playback/telemetry`——接收 vaultflix 播放器回報的播放進度與事件。

**狀態：待補（Day 11 前補上詳細規格）**

需要在 Day 11 前定稿的內容：

- [ ] request / response schema（欄位、型別、必填與否）
- [ ] 認證與授權要求
- [ ] 資料寫入目標與 schema 變更
- [ ] 錯誤處理與狀態碼定義
- [ ] 節流／批次上報行為
- [ ] 必須通過的測試清單
- [ ] 明確排除的範圍（不做什麼）

> spec 一經定稿即凍結，三輪之間不得修改，否則失去校準意義。執行中若發現 spec 有缺陷，記錄在該篇文章裡，但不改 spec。

### 附註：這個 endpoint 不只是校準用的題目

Day 12 上線的這個 endpoint 在系列期間會持續收數據。它同時是校準任務的標的，也是一組真的在跑的生產遙測。

Day 28 的 Plan B 就是用這批累積下來的數據，回答 ROADMAP 上 ABR（自適應位元率）的觸發條件：外網實際的 rebuffer ratio 有沒有高到值得做 ABR。也就是說 Day 12 的產出到 Day 28 會被回頭檢驗一次——不是檢驗「AI 寫得對不對」，而是檢驗「這份數據夠不夠拿來做決策」。

這也表示 spec 裡的欄位設計要考慮到後續分析需求（至少要能算出 rebuffer 次數、rebuffer 時長、播放總時長），這部分在 Day 11 定稿時一併想清楚。

## 五、預註冊表

動工前填寫驗收標準與難度預估，用來對照事後的實際結果。
事前預估與事後結果的落差本身就是本系列的觀察對象之一，尤其是「我以為簡單但實際卡住」的項目。

**狀態：待補（Day 11 前填寫）**

| 功能標的 | 框架 | 驗收標準（事前定義） | 事前難度預估（1–5） | 預估往返輪數 | 最擔心的失敗點 |
| --- | --- | --- | --- | --- | --- |
| 校準任務：播放遙測 endpoint | 三輪共用 | 待補 | 待補 | 待補 | 待補 |
| 即時轉碼 | superpowers | 待補 | 待補 | 待補 | 待補 |
| 全文搜尋 | agent-skills | 待補 | 待補 | 待補 | 待補 |
| API Gateway | Matt Pocock skills | 待補 | 待補 | 待補 | 待補 |

填寫規則：

- 驗收標準必須是可判定的。「能跑」不算，「原本不能播的 N 部片，轉碼後 N 部都能在瀏覽器播完」才算。
- 預註冊表填完就不再修改。事後若覺得標準訂錯了，在文章裡說明，但不回頭改表。
- 事後結果寫在各篇文章的驗收章節，Day 26（三框架比較彙整）時統一對照。
